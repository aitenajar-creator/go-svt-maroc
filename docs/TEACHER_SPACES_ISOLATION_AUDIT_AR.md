# تدقيق عزل فضاءات الأستاذ والتلميذ ومجتمع الأساتذة

**التاريخ:** 17 نوفمبر 2026  
**المستودع:** `aitenajar-creator/go-svt-maroc`  
**النطاق:** مراجعة إعدادات الاتصال وسياسات RLS الحية في مشروعي Supabase، مع قراءة ملفات الواجهة وملفات migrations. لا يتضمن هذا التدقيق اختبار اختراق أو محاكاة حسابات فعلية.

## الخلاصة

توجد بنية فصل واضحة بين فضاء الأستاذ الإداري/الأقسام ومجتمع الأساتذة المستقل:

- المشروع الرئيسي: `faztvkeyrxvmjzzfuyiu`، ويضم حسابات التلاميذ والأساتذة والإدارة وبيانات الأقسام.
- مشروع المجتمع: `gymofjissiuwpnaxsmcw`، ويضم مصادقة مستقلة للأعضاء وموارد المجتمع ومخزن الملفات الخاص.
- ملف `teacher-community-config.js` يشير إلى مشروع المجتمع ومفتاح Publishable الخاص به فقط.
- ملف `supabase-config.js` يشير إلى المشروع الرئيسي.
- مجتمع الأساتذة يستعمل مفتاح جلسة مستقل `gosvt_teacher_community_auth_v1`، بينما عميل المشروع الرئيسي يحتفظ بجلسة المشروع الخاص به.

وبذلك لا يؤدي استخدام البريد الإلكتروني نفسه إلى دمج حساب المجتمع بحساب الأستاذ أو التلميذ في المشروع الرئيسي.

## ما تم التحقق منه في المشروع الرئيسي

- RLS مفعّل على `profiles` و`teacher_classes` و`teacher_class_students` وبيانات التقدم والملاحظات والمفضلة.
- سياسات فضاء الأقسام تقيد إدارة القسم بالأستاذ المسند إليه أو مدير المنصة، وتسمح للتلميذ بالوصول إلى بيانات الأقسام التي انضم إليها فقط.
- سياسات التقدم والملاحظات والمفضلة تربط السجلات بمعرّف المستخدم المصادق عليه.
- يوجد المشغل `profiles_prevent_role_change` قبل تحديث سجل الملف الشخصي، ويستدعي `prevent_profile_role_change()` لحماية الدور من تغييرات العميل.

## ما تم التحقق منه في مشروع المجتمع

- RLS مفعّل على جداول الأعضاء والموارد.
- جدول `teacher_community_admins` محمي بـ RLS ولا توجد له سياسات مباشرة؛ تتحقق دالة الإدارة ذات الصلاحية المحددة من هوية المدير.
- التسجيل الذاتي لا يسمح إلا بإنشاء عضوية حالتها `pending`.
- تحديث حالة العضوية متاح للإدارة فقط.
- قراءة المورد متاحة لصاحبه أو الإدارة أو العضو المقبول عندما يكون المورد منشوراً ومشتركاً.
- إضافة المورد تتطلب أن يكون مالكه هو المستخدم الحالي وأن تكون العضوية مقبولة (أو أن يكون المستخدم مديراً).
- سياسة التعديل الحية تشترط عضوية مقبولة للمالك، مع استثناء الإدارة.
- الحذف متاح لصاحب المورد أو الإدارة، وسياسة Storage للحذف تقيد مسار الملف بمعرّف صاحبه أو تسمح للإدارة.
- مخزن `teacher-community` خاص، والتنزيل يتم بروابط موقعة قصيرة الأجل.
- سياسة قراءة Storage تربط الملف بسجل المورد وتطبق شروط الملكية/الإدارة/المشاركة والعضوية المقبولة.
- سياسة تحديث Storage تشترط العضوية المقبولة للمالك، أو صلاحية الإدارة.

## نتائج إصلاحات العضو المعلّق

تم تطبيق migration `20261117000100_restrict_suspended_teacher_community_updates.sql` على مشروع المجتمع. وأكد استعلام `pg_policies` الحي شروط العضوية المقبولة في سياستي تحديث الموارد وStorage.

كما تم تعديل مسار الحذف للعضو المعلّق: يحذف الملف الخاص من Storage أولاً، ثم يحذف سجل المورد. إذا فشل حذف الملف يبقى السجل حتى يمكن إعادة المحاولة. هذا المسار لا يطلب تحديثاً محظوراً لبيانات المورد.

## ملاحظات المتابعة

1. يعرض Supabase Security Advisor تحذيراً لأن دالتي `gosvt_teacher_community_is_admin()` و`gosvt_teacher_community_is_approved_member()` من نوع `SECURITY DEFINER` وقابلتان للاستدعاء من دور `authenticated`. الدالتان تضبطان `search_path = public` وتعيدان قيمة منطقية تخص المستخدم الحالي، كما تحتاجهما الواجهة وسياسات RLS. لا يُنصح بسحب EXECUTE منهما دون إعادة تصميم الاستدعاء وسياسات الوصول.
2. حماية كلمات المرور المسرّبة معطلة في إعدادات Auth لمشروع المجتمع وفق Security Advisor. يتطلب تفعيلها مراجعة إعدادات لوحة Supabase واختبار التسجيل وتغيير كلمة المرور؛ لم يتم تغيير إعداد Auth من هذا التدقيق.
3. لا يمكن اعتبار حذف الملفات أو التنزيل قد اجتاز اختباراً وظيفياً كاملاً لمستخدمين مختلفين؛ التحقق الحالي مبني على تعريفات السياسات الحية ومراجعة مسارات JavaScript.
4. يوصى بإجراء اختبار قبول يدوي بحسابات اختبار مستقلة: عضو pending، عضو approved، عضو suspended، ومدير؛ مع التأكد من عدم استخدام حسابات حقيقية أو بيانات إنتاج حساسة.

## حدود التدقيق

هذه مراجعة إعدادات ومصدر وسياسات قاعدة البيانات الحية، وليست شهادة أمنية أو اختباراً شاملاً لجميع المسارات. لم يتم تعديل بيانات المستخدمين أو تغيير أدوارهم أو حذف موارد فعلية أثناء المراجعة.
